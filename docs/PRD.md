# CarbonBit v0.1

## Product Requirements Document
| Field | Value |
| --- | --- |
| Product | CarbonBit |
| Version | v0.1 |
| Product type | VS Code Extension |
| Primary platform | Visual Studio Code |
| Status | MVP definition |
**Primary goal:** Make the environmental impact of AI-assisted software development visible through real-time environmental metrics and a reactive 16-bit visual world.

---

# 1. Product Summary
CarbonBit is a VS Code extension that estimates the environmental impact generated by AI-assisted development.

The extension collects local usage information from supported AI coding tools, normalizes token and model usage, estimates energy consumption, CO₂e emissions, and water usage, and presents the results through a persistent 16-bit animated environment inside the VS Code sidebar.

The core differentiator is not the analytics dashboard.

The core differentiator is the **live 16-bit world**, which reacts while AI is being used.

When no AI activity is happening, the environment remains calm. When an AI request starts, a data center activates, electricity flows through the scene, cooling systems become active, and the environment visually represents the relative size of the request.

CarbonBit must clearly communicate that environmental figures are **estimates**, not direct measurements.

---

# 2. Product Vision
Make the environmental cost of AI-assisted software development understandable without requiring developers to understand infrastructure metrics.

CarbonBit should turn abstract values such as:

- tokens
- watt-hours
- grams of CO₂e
- water consumption

into something developers can immediately understand and observe while working.

The product should encourage awareness and efficiency.

It should not attempt to discourage AI usage.

---

# 3. Product Positioning
CarbonBit is:

> A live environmental monitor for AI-assisted software development.

CarbonBit is not:

- an AI productivity tracker
- an employee monitoring tool
- a prompt quality analyzer
- an AI proficiency scoring system
- an exact carbon calculator
- a cloud cost management platform

The main questions CarbonBit answers are:

1. What AI tools and models am I using?
2. How much AI am I using?
3. What is the estimated environmental impact?
4. What is happening right now?
5. How confident is CarbonBit in each estimate?

---

# 4. Target Users

## Primary Persona

### AI-Assisted Developer
A software developer using tools such as:

- GitHub Copilot
- GitHub Copilot CLI
- Claude Code
- Codex CLI

Characteristics:

- uses AI repeatedly throughout the working day
- may use multiple AI providers
- understands tokens at a high level
- does not understand how tokens translate into environmental impact
- wants lightweight feedback without interrupting development

### Main Jobs to Be Done

> When I use AI while coding, I want to understand its approximate environmental impact so that I can make more informed decisions about how I use AI.

> When I use different models, I want to understand that they may have significantly different resource requirements.

> When CarbonBit presents environmental figures, I want to understand how reliable those estimates are.

# 5. Goals

## v0.1 Goals
CarbonBit v0.1 must:

1. Detect AI usage from supported local tools.
2. Collect or estimate token usage.
3. Identify the model when possible.
4. Estimate energy consumption.
5. Estimate CO₂e emissions.
6. Estimate water consumption.
7. Aggregate usage for the current day.
8. Store usage locally.
9. Display a persistent VS Code sidebar view.
10. Show a reactive 16-bit animated environment.
11. Show current AI activity.
12. Show environmental totals.
13. Show usage by provider.
14. Clearly communicate estimate confidence.
15. Work without a cloud backend.

# 9. Provider Adapter Interface
Every provider integration must expose a common interface.

Example:

```typescript
interface AiProviderAdapter {
    id: string;
    displayName: string;

    isAvailable(): Promise<boolean>;

    start(): Promise<void>;

    stop(): Promise<void>;

    onUsageEvent(
        callback: (event: AiUsageEvent) => void
    ): Disposable;
}
```

Adapters are responsible only for discovering and parsing provider data.

They must not calculate environmental impact.

---

# 10. Normalized AI Usage Event
All providers must emit a common event structure.

```typescript
interface AiUsageEvent {
    id: string;

    provider:
        | "github-copilot"
        | "github-copilot-cli"
        | "claude-code"
        | "codex-cli";

    model?: string;

    startedAt: string;

    completedAt?: string;

    inputTokens?: number;

    outputTokens?: number;

    cachedInputTokens?: number;

    cacheCreationTokens?: number;

    source:
        | "actual"
        | "estimated";

    status:
        | "started"
        | "processing"
        | "completed"
        | "failed";
}
```

The data model must support partial information.

For example, the extension may know that a request started before token counts are available.

---

# 11. Data Collection Strategy
CarbonBit must prioritize local data sources.

The preferred order is:

1. Actual provider session data.
2. Actual token counters from local logs.
3. Token estimates derived from text length.
4. Generic fallback estimation.

CarbonBit must not require API keys in v0.1.

CarbonBit should avoid sending data to external services.

---

# 12. Local-First Privacy Model
CarbonBit v0.1 must operate entirely locally.

The extension must not upload:

- prompts
- responses
- source code
- file names
- repository contents
- token histories
- environmental statistics

No telemetry should be enabled by default.

If telemetry is introduced later, it must be opt-in.

---

# 13. Environmental Impact Engine
The environmental engine converts normalized AI usage into environmental estimates.

Example interface:

```typescript
interface EnvironmentalImpact {
    energyWh: number;

    carbonGrams: number;

    waterLiters: number;

    confidence:
        | "high"
        | "medium"
        | "low";

    methodology: string;
}
```

---

# 14. Estimation Hierarchy
CarbonBit should use the following hierarchy when estimating environmental impact.

## Level 1
Published model-specific measurement.

Confidence:

**High**

Example:

```text
Exact model identified
+
published measurement available
```

---

## Level 2
Published measurement for the model family.

Confidence:

**Medium**

Example:

```text
Claude Sonnet 4.x
estimated using Claude Sonnet family data
```

---

## Level 3
Model-class estimate.

Confidence:

**Medium / Low**

Example categories:

- small
- medium
- frontier

---

## Level 4
Generic inference estimate.

Confidence:

**Low**

Used only when no meaningful model information exists.

---

# 15. Environmental Database
CarbonBit should maintain its environmental model factors separately from application logic.

Example:

```json
{
  "models": {
    "claude-sonnet": {
      "category": "medium",
      "confidence": "medium",
      "methodology": "published-family-estimate"
    }
  }
}
```

Do not hardcode environmental values throughout the codebase.

Create a versioned methodology dataset.

Example:

```text
data/
    environmental-models.json
    environmental-methodology.json
```

This allows environmental assumptions to evolve independently from the UI.

# 20. 16-Bit World
The pixel environment is the primary interaction surface.

It must react to AI usage.

The world should contain:

- developer character
- laptop/workstation
- trees
- sky
- ground
- data center/server building
- electricity effects
- cooling/water effects
- network/data particles

The visual design should resemble a polished 16-bit game.

Avoid copying specific commercial game assets or styles.

---

# 21. World States
The world must use an explicit state machine.

```typescript
enum WorldState {
    Idle,
    RequestStarting,
    ProcessingLight,
    ProcessingMedium,
    ProcessingHeavy,
    ResponseArriving,
    Failed
}
```

---

# 22. Idle State
When no AI request is active:

- developer sits at laptop
- subtle typing animation may occur
- trees move slightly
- birds/clouds may move
- data center remains mostly inactive
- environment remains calm

Animations should be intentionally subtle to avoid distracting the developer.

---

# 23. Request Starting
When an AI request is detected:

- developer types
- small data particles leave the laptop
- particles travel toward the data center
- data center lights activate

Duration:

Approximately 500-1000 ms.

---

# 24. Processing States
The visual intensity should depend on the estimated model category.

## ProcessingLight
Examples:

- smaller models
- lightweight requests

Animation:

- small amount of electricity
- limited server activity
- subtle cooling animation

---

## ProcessingMedium
Animation:

- multiple server windows active
- more electrical particles
- visible cooling flow
- stronger animation

---

## ProcessingHeavy
Animation:

- full data center activity
- stronger electricity effects
- more cooling animation
- more network particles
- environmental scene becomes temporarily more industrial

The intent is comparison, not guilt.

---

# 25. Response Arriving
When generation completes:

- data particles move from data center back to laptop
- developer receives response
- short completion animation
- impact counters update
- environment transitions back to idle

---

# 26. Failed Request
If the AI request fails:

- red/orange server indicator
- data transmission stops
- brief failure animation
- environment returns to idle

Do not represent failed requests as zero impact if usage data indicates tokens were still consumed.

---

# 35. Rendering Performance
The animation must not noticeably affect VS Code performance.

Targets:

- idle CPU usage close to zero
- animation capped at 30 FPS
- pause rendering when sidebar is hidden
- pause animation when VS Code loses focus if appropriate
- avoid unnecessary extension-host work
- aggregate events before frequent UI updates

The visual experience is important, but developer tooling performance has priority.

CarbonBit v0.1 can be released when the following user journey works:

1. User installs CarbonBit.
2. CarbonBit detects at least one supported provider.
3. User opens the CarbonBit sidebar.
4. Pixel world renders.
5. CarbonBit detects an AI interaction.
6. Pixel world switches from idle to processing.
7. Provider and model are displayed.
8. Token usage is collected or estimated.
9. Environmental impact is calculated.
10. Animation reacts according to request size/model class.
11. Request completion returns the world to idle.
12. Today's statistics update.
13. Usage persists after restarting VS Code.
14. User can inspect calculation confidence.
15. User can inspect methodology.
16. User can clear all locally stored data.

# 56. Product Risks

## Risk: Environmental estimates appear scientifically precise
Mitigation:

- always use "estimated"
- expose confidence
- document assumptions
- separate measurements from heuristics

---

## Risk: Provider session formats change
Mitigation:

- isolated adapters
- defensive parsing
- schema tests
- adapter-level diagnostics

---

## Risk: Animation becomes distracting
Mitigation:

- subtle idle animation
- 30 FPS cap
- minimal mode
- reduced-motion support
- pause hidden views

---

## Risk: Scope expands into generic AI analytics
Mitigation:

Every proposed feature should pass this test:

> Does this help a developer understand or reduce the environmental impact of AI usage?

If not, it should probably not be part of CarbonBit.
